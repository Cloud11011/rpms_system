## 4. Audit retention: current behaviour, implications and recommendation (scope item 4)

### 4.1 What the reviewed purge does today (`includes/account_retention.php`, `retention_purge_mutate()`)

**For each purged Student**, it **deletes** every audit row where any of these holds:
- the row's document is one of that Student's documents;
- the row's report is one of that Student's reports;
- `student_id` is that Student, or the entity is that Student;
- `user_email` is one of that Student's current or previous emails, unless another account now uses it;
- the row is a `student_saved` row naming that Student ID;
- the entity is that Student's login.

It then **writes one new audit row** (Admin actor, method, reason, Student ID or "student account #id") and an `account_purge_jobs` row with a manifest SHA-256. Both are kept.

**For a completed Adviser**, it keeps the rows and removes only the entity link (`entity_id` set to NULL). A never-completed Adviser's rows are deleted.

The design erases a removed person's history and keeps proof of the erasure.

### 4.3 Implications

- The live audit trail would no longer show **what Administrators did to these test accounts**: invitations, reviews, summaries, overrides, archive/restore. Each purge still proves who removed which account, when and why.
- All subjects are confirmed test identities, so no data-subject privacy reason requires erasing these rows. The purge erases them because it is designed for real people.
- **No retention period for audit records was found in the repository.** RPMS must state it.

### 4.4 Options

| Option | What | Code change | Result |
| --- | --- | --- | --- |
| **A (recommended)** | **Retention extract before cleanup.** On the verified pre-cleanup restore, export exactly the rows listed in the signed preview's `auditImpact.predictedRemovalIds`, read-only: `SELECT * FROM activity_logs WHERE id IN (…)`. Record the extract's SHA-256 in the cleanup manifest, and store it with the verified backup, under RPMS's retention period and access rule. The live purge stays exactly as reviewed. | None | Audit history preserved off-line and accounted for row by row; the verifier proves nothing else was removed |
| B | Change the purge to **pseudonymize** Admin-actor rows instead of deleting them (keep action, actor, time, reason; drop the Student link and identifying details) | Yes, in a deletion-safety path used for real people | Needs privacy review and full regression. **Not recommended** before this release. |

**Recommendation: A**, with RPMS approving the extract's retention period and storage. **Until RPMS approves A (or another option), the production cleanup stays blocked.** The staging rehearsal can proceed, because staging is a disposable copy.

## 6. Deletion verification-key generator

| | |
| --- | --- |
| Tool | [`maintenance/issue-deletion-verification.php`](../maintenance/issue-deletion-verification.php) |
| No-SSH route | `deletion-verification` step in `maintenance/hostinger-cron-runner.php` |

It uses only the reviewed issuers in `includes/account_lifecycle_schema.php` and self-validates with the application's own validator.

**Safeguards:**
- CLI only; never loads `config.php`; explicit DSN with optional verified TLS.
- `--expect-db` must match the connected database.
- The key comes from the environment and is never printed.
- Holds the `prism_migrate` mutex.
- Shared-hosting mode requires the `--external-dependencies-excluded` attestation.
- `--out` is required (SEC-01, independent review): the evidence goes only to a new file in a private directory outside the application (mode 700, owned by the account, no links). The file is created exclusively with mode 600 before any content is written. Stdout carries a host-free summary; the evidence is never printed.
- The cron receipt is checked to contain no key, password, DSN or host.

**Tested on isolated databases only:**
- 4 invocation refusals;
- the application rejected evidence issued with another key, and tampered evidence;
- the cron route worked with a clean receipt;
- issuance on the restored export.

**Status: ready for independent review** ([12](12_PRE_STAGING_READINESS_REPORT.md)). Each deployment needs its own `PRISM_HARD_DELETE_VERIFICATION_KEY` in `config.local.php`, and the evidence must be re-issued after any schema change.

## 8. Acceptance criteria (staging cleanup rehearsal; repeated for production)

1. Exactly Administrators 1, 13, 46 exist, with unchanged fingerprints; each Admin's deadlines, groups, notices, campaigns, acceptances and reset rows are unchanged; legal, staff-code, stage-label and schema-meta rows are unchanged (`verify-final` checks).
2. 0 Students, 0 Advisers, 0 non-Admin logins, 0 documents, 0 IERB history, 0 deadline recipients, 0 Student-owned AI outputs, 0 non-Admin invitations or resets, 0 pending purge jobs.
3. Reports: 28 institution-wide reports at the end of the cleanup window; 0 after the separately authorized deletion.
4. **Audit accounting PASS:** every pre-existing audit row outside the signed prediction still exists; the removed count is recorded. Under option A, the extract's SHA-256 is recorded.
5. Only the 6 identified orphaned notifications remain addressed to Students.
6. Each Administrator signs in and opens the nine main pages; Student, Adviser, document and report lists are empty.
7. Runtime preflight: contract PASS at the database's schema.
