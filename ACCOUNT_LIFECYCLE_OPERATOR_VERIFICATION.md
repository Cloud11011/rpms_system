Account hard deletion is disabled by default. Archive is independent of this gate.

Before enabling it, an authorized operator must verify the actual deployment database with complete server metadata visibility. A successful query using schema-scoped web credentials does not establish completeness. Do not increase the web account's privileges merely to satisfy this prerequisite.

1. Disable `PRISM_HARD_DELETE_SCHEMA_VERIFIED` during all schema maintenance. Exclude concurrent DDL affecting this database and incoming references from other databases. Application migrations and hard deletion share the existing `prism_migrate` advisory lock; that lock does not prevent an administrator from running arbitrary DDL elsewhere.
2. Supply separately authorized verifier credentials through `PRISM_SCHEMA_VERIFY_HOST`, `PRISM_SCHEMA_VERIFY_PORT`, `PRISM_SCHEMA_VERIFY_DATABASE`, `PRISM_SCHEMA_VERIFY_USER`, and `PRISM_SCHEMA_VERIFY_PASSWORD`. Use a controlled environment; do not put passwords in command arguments or reports.
3. Run `php tools/verify-account-lifecycle-schema.php --verify --schema-changes-excluded`. This CLI does not load application configuration, call migrations, seed records, or write database data. Its inventory transaction is read-only. It requires direct global SELECT and TRIGGER visibility and refuses schema-scoped or unrecognized inherited-role arrangements conservatively.
4. Review the result. The verifier checks engines, columns including defaults, index components, fully qualified local/incoming foreign keys and their rules, triggers, and schema version against `includes/account_lifecycle_schema.json`. Any mismatch leaves hard deletion disabled. Do not change the database or loosen the manifest to force a match without a separate review.
5. Only after successful verification and operational approval, place both exact configuration definitions emitted by the verifier into the deployment's protected `config.local.php`. The required definitions are `PRISM_HARD_DELETE_SCHEMA_VERIFIED` set to boolean true and `PRISM_HARD_DELETE_VERIFICATION` containing the generated manifest SHA-256, database/server binding, complete-visibility assertion, and schema-maintenance exclusion assertion. Setting the boolean alone does not enable deletion.

Runtime checks still compare the actual visible metadata on every permanent-delete request. The approval is bound to the database name, server hostname/port/server ID/version, and exact reviewed manifest. A moved/upgraded database or changed manifest requires fresh verification. Keep the DDL exclusion in force for the entire enabled period; limited web metadata visibility cannot detect a new external dependency hidden from that account. Disable deletion before maintenance, revoke the old approval, and repeat verification afterward. If hosting cannot provide an authorized verifier with complete visibility, retain Archive and keep permanent deletion disabled.

Archive deactivates one confirmed owned login and invalidates its reset/setup tokens transactionally. Ambiguous ownership requires Admin review; it never deactivates every matching email or silently reports success. Admin lifecycle is self-only and always retains another active Admin.

Student and Adviser permanent deletion is deliberately limited to unused records with trustworthy, unchanged creation provenance. Existing legacy records without that provenance and records with identity changes remain archive-only. Never backfill creation markers to make them eligible. Documents, significant IERB history, frozen recipients, protected notifications/workflow evidence, uncertain reports/AI references, and other ownership dependencies prevent deletion. No institutional history is removed or nulled to clear a conflict.

Concurrency validation covers MariaDB 10.4.32 with explicit READ COMMITTED and REPEATABLE READ, including the actual local REPEATABLE READ default. Deployments using a different isolation level or additional account/reference writers require validation before enabling hard deletion. All application writers must follow the parent-row locking protocol; direct SQL/import jobs bypassing it are outside that protocol and must be coordinated operationally.

These instructions document a prerequisite only. This implementation did not enable deletion in installed application configuration or perform a production database change.
