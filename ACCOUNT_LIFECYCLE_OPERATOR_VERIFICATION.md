# Persistent permanent-deletion deployment verification (Batch 10.5)

Permanent deletion is disabled by default; Archive remains independent. Current source uses frozen schema v10. This procedure is operator documentation only and authorizes no deployment, database access or configuration change.

## Trust and lifetime

Version-3 evidence is authenticated with HMAC-SHA256 using a unique random 256-bit installation key. It is installed with the existing protected PHP configuration, not served as a public file or API payload. The key is separate from database credentials. Both key and evidence must remain in protected `config.local.php` (or the key may be supplied through the operator-only verifier environment during generation). Never place them in URLs, JavaScript, browser storage or downloadable artifacts. The existing Apache protection of `config.local.php` must remain installed; prefer an operator-managed include outside the web root where hosting permits it.

There is no fixed-time expiry and no scheduled renewal. `issued_at` is informational Unix-time metadata; its age does not affect validity. Version 1/2 evidence, missing authenticators, unsupported versions, unexpected fields, malformed data or any legacy `expires_at` field fail closed. After deploying version-3 code, one newly authenticated verification is necessary; old evidence cannot be promoted by editing dates or its version.

Evidence binds the exact manifest SHA-256, database name, server hostname/port/server ID/version, mode, schema-change exclusion, and verifier contract. The contract fingerprint hashes the exact bytes of `includes/account_lifecycle_schema.php` and, for v10, `includes/schema_v10.php` and `includes/schema_v10_plan.json`. Scoped evidence additionally binds visible schemas, direct SELECT/TRIGGER grants and the visible metadata fingerprint. A unique installation key prevents replay into a different installation using a different key. Reusing/copying the key and evidence deliberately into an identical environment defeats that separation; protect operator configuration.

CSS/text edits outside these bound files do not invalidate evidence. Manifest, bound verifier files, database/server identity, key rotation, missing/corrupt evidence and live protected metadata/invariant changes disable deletion. Keep deletion disabled throughout relevant maintenance and reverify only after a protected invariant changes. There is no automatic regeneration or persistent cross-request verification cache.

## Verification modes and live checks

- `--verify --schema-changes-excluded` is globally privileged operator verification. It requires direct global SELECT and TRIGGER grants and never falls back to scoped mode. The web connection may have scoped grants, but now must prove direct schema-wide SELECT/TRIGGER visibility for every application schema it sees. Visible application triggers, unresolved rules and visible cross-schema PRISM dependencies are rejected during both generation and runtime validation.
- `--verify-shared-hosting --schema-changes-excluded --external-dependencies-excluded` is explicit shared-hosting verification. It requires direct schema-wide SELECT and TRIGGER grants on every visible application database. Table/column-only grants or unrecognized inherited roles are insufficient. Evidence records `complete_visibility=false` and binds the exact visible assessment; it never becomes a claim of unrestricted visibility.

Every Admin availability call and every destructive operation repeats authenticity, binding, SHOW GRANTS, SHOW DATABASES, visible tables, FK components/rules, triggers, the manifest inventory, schema version, frozen-v10 constraint checks and session `foreign_key_checks=1`. Inventory covers table engines, ordered column types/nullability/defaults/keys, indexes/uniqueness and ordered components, FK schema targets and update/delete rules. Database/query/visibility errors disable deletion. API messages contain only operator-contact guidance; technical verification exceptions go to protected server logs. No evidence, keys or fingerprints are returned by availability.

Actual purge, Admin self-deletion and recovery retain the `prism_migrate` advisory lock and repeat the verifier independently of any earlier browser response. Actor/password checks, archive-first eligibility, seven-day manual grace, six-calendar-month cleanup retention, single-account override, Hold, unresolved-workflow checks, row locks, file quarantine, audit and notification/support integration are unchanged.

## Shared-hosting limitations

Metadata cannot prove absence of invisible incoming cross-schema references or invisible external trigger/definer writes. The scoped operator must establish and maintain isolation with the hosting provider and other database operators. Hidden CASCADE/SET NULL dependencies are not stopped by enabled foreign-key checks; hidden RESTRICT references fail and roll back. Arbitrary external DDL does not obey PRISM's advisory lock. These operational exclusions remain continuously necessary with persistent evidence. If they cannot be maintained, leave deletion disabled and use Archive. Loss of required visible privileges never counts as a successful empty metadata check.

## Operator installation without server SSH

Ordinary RPMS Admins need no CLI, passwords, phpMyAdmin or periodic verification work. A technical operator performs this procedure only after initial deployment or a relevant invalidating change, under separate production authorization.

1. Keep `PRISM_HARD_DELETE_SCHEMA_VERIFIED=false` while deploying a matching reviewed code/manifest and establishing the continuous DDL/external-dependency exclusion. Never upload local credentials or overwrite production secrets. Do not run a migration for Batch 10.5.
2. Generate a unique 32-byte random key privately, represented by exactly 64 lowercase hexadecimal characters, using the operator's secure local tooling. Install it as `PRISM_HARD_DELETE_VERIFICATION_KEY` in protected deployment configuration. Do not reuse another installation's key. Provide the same key to the local verifier as `PRISM_SCHEMA_VERIFY_KEY`; never paste it into command arguments, logs or shared reports.
3. Without server SSH, use the established locally run PHP verifier and temporary Hostinger Remote MySQL access under separately authorized operator control. phpMyAdmin can inspect discrepancies, but manual inspection/SQL results cannot create authenticated evidence and a boolean is insufficient. The local checkout must have exactly the bound deployed files; Remote MySQL and web routes must reach the same database/server. No root/global privileges are assumed for scoped mode.
4. Supply `PRISM_SCHEMA_VERIFY_HOST`, optional `PRISM_SCHEMA_VERIFY_PORT`, `PRISM_SCHEMA_VERIFY_DATABASE`, `PRISM_SCHEMA_VERIFY_USER`, `PRISM_SCHEMA_VERIFY_PASSWORD` and `PRISM_SCHEMA_VERIFY_KEY` through the operator process environment. Prompt for password/key securely, and clear these variables immediately afterward. Execute one of:

```text
php tools/verify-account-lifecycle-schema.php --verify --schema-changes-excluded
php tools/verify-account-lifecycle-schema.php --verify-shared-hosting --schema-changes-excluded --external-dependencies-excluded
```

5. The CLI loads no application config, invokes no migrations/seed routines, uses a read-only transaction and emits only the two existing PHP evidence/gate definitions on success. It never prints the signing key or database password. Review the mode, deployment identity and scoped assessment privately. On any refusal, leave the gate false.
6. In the existing protected production `config.local.php`, replace the old gate/evidence definitions with the exact two emitted `define(...)` statements. Preserve the separately installed key and all other secrets. Do not duplicate definitions, edit fields or copy local-test evidence. This is a manual operator action; Batch 10.5 performs no configuration installation.
7. Reload Archived Accounts. Valid deployment verification says **Permanent deletion available**, while account-specific controls still distinguish retention, Hold and workflow blocks. Invalid verification says **Permanent deletion is unavailable because deployment verification is required. Contact the system operator.** A valid availability response never authorizes a later purge.
8. Revoke temporary Remote MySQL access when done. Leave authenticated evidence installed for ordinary use while the deployment invariants and isolation remain intact; elapsed time never requires renewal. Disable the gate before relevant maintenance, revoke/rotate the key if configuration trust is lost, and reverify only after an invalidating change.

The historical lifecycle notes below are retained for reference. Their migration/deployment actions are outside Batch 10.5 and require separate authorization; their current evidence policy is the version-3 policy above.

This section documents the historical v9 transition; current verification requires the frozen final v10 deployment. If an intermediate v9 was applied to a persistent database, stop and require a separately reviewed new migration version; the existing version-9 stamp does not upgrade that database. Keep purge disabled and block application writers for a backed-up maintenance window. First validate the complete code/migration against an isolated copy on the actual hosting MariaDB version. The base prerequisite is the reviewed v8 schema. Do not reuse old verification evidence: v9 changes its manifest hash.

Choose one reviewed path:

This dedicated tool checks the configured DB name, takes the existing migration lock, applies additive changes and does not seed accounts. Existing v6/v7/v8 migration guards remain necessary if the starting database predates v8. Remove the migration environment flags immediately afterward. Do not leave automatic web DDL enabled.
- Without SSH, use phpMyAdmin to select the exact database and import the separate [schema-v9-retention-manual.sql](tools/schema-v9-retention-manual.sql). Edit only its `@PRISM_V9_EXPECT_DB` and `@PRISM_V9_BACKUP_AND_STAGING_VERIFIED` settings after backup/staging review. It requires MariaDB 10.4+ and permission to create/alter/drop a temporary stored procedure, plus schema DDL. Ask the provider to execute the reviewed script if those permissions are unavailable. The protected existing `tools/schema-v8-manual.sql` is not part of this migration.

Both paths keep foreign-key checks enabled, preserve all existing relationships, add only the invitation user CASCADE and inviter SET NULL foreign keys, validate the exact final column/index/FK/table/trigger inventory, and advance `schema_version` only after successful validation and backfill. These narrow invitation FKs do not authorize deleting unknown dependencies. MariaDB DDL commits implicitly: a failed migration can leave additive fields/indexes. Keep the site in maintenance, inspect the failure and retry the entire reviewed migration; do not stamp the version manually. The manual procedure may remain after a failed CALL; a retry replaces that procedure. Backups are operator controlled, with restoration planned before the maintenance window.

Changes: Adviser `archived_at`; both account types' structured Hold metadata, last purge-postponement metadata and `restored_at`; explicit nullable Student/report/AI ownership; historical `calendar_deadlines.creator_name`; `account_purge_jobs` durable minimal recovery state; retention, ownership, recipient, file/version and audit indexes. Old data is preserved. Legacy inactive Advisers without a date receive the migration time, so they receive a fresh grace/retention period. Student archive dates remain. Legacy report/AI ownership is never inferred from names, titles or `source_ref`.

After migration deploy the complete reviewed application/manifest together in the separately authorized window, then follow the no-SSH verification procedure above. The verifier must accept the exact v9 inventory before enabling purge. Keep CLI tools, tests and reports outside the public site. Ensure private storage and `.purge` are not web readable, writable only by the application, and on the same filesystem as document/report storage. The existing root/storage access controls must remain installed. Back up DB and uploaded storage consistently.

## Final combined v9 invitations and onboarding

The final migration keeps identity uniqueness and relaxes only six name/ID columns: users.username/full_name, students.student_id/full_name and advisers.employee_id/full_name. Email and password hash remain required. Both profiles receive nullable profile_completed_at and a completion index. account_invitations holds one purpose-bound setup state per login with a hashed token, expiry, acceptance time and inviter reference. No placeholder name, institutional ID or research group is stored.

Legacy profiles are marked complete at their original created_at only when a same-role login has the same email/name/username/ref_id, the profile ID/name/email are nonblank with email shape, the explicit user_id is absent or correct, and no competing same-role link, cross-role profile claim or invitation exists. Historical academic values stay intact. Malformed, orphaned and ambiguous records remain incomplete for reviewed Admin identity repair; they are not auto-invited or silently reclaimed. Review affected records in an isolated deployment copy before the migration. This work did not query installed records or determine real counts.

Admin can Invite Student with email alone and an optional active, complete Adviser, or Invite Adviser with email alone. A complete active Adviser can Invite Student; the server assigns the Student to that authenticated Adviser and rejects supplied assignment/privilege fields. Students and incomplete Advisers cannot invite. Existing Add Record and IERB complete-record creation remain available. Emails claimed by any active, Pending, archived, opposite-role or orphaned identity are refused. Review the existing record rather than creating another account or implicitly restoring it.

Invitation creation commits the Pending account before attempting sensitive email delivery. Delivery failure leaves one valid Pending identity and an actionable result. Authorized staff can use Resend Invitation after the 60-second cooldown; it rotates the one-hour secret and invalidates older links. Admin can resend both types; Advisers can resend only their currently assigned Pending Students. Completed or already accepted invitations cannot be resent as first-time setup; use ordinary recovery for an accepted account. Configure the canonical APP_BASE_URL and existing allowed institutional email domains/transport through the normal separately authorized configuration process.

Setup links carry the secret in a browser fragment, which is consumed and removed by the setup page; it is never placed in a normal URL query/access log. JavaScript is required to open that link. The server accepts the secret only in a protected POST, validates the current bound profile/login and expiry, hashes the new password, consumes the token once, and invalidates resets atomically. No temporary password is emailed. Then the user signs in with the invited email, completes their profile, and reaches the normal role workspace. Central page/API guards allow only completion, password security and logout while Pending.

Students supply full name, first-set Student ID, canonical academic unit/program/year level/academic year, and optional research title. Graduate program unit/year behavior follows the existing catalog. Advisers supply full name, first-set Employee ID and a catalog department. IDs are trimmed, nonempty, bounded to 100 characters, reject controls and must be unique across retained identities; later self-edit is forbidden and Admin correction remains available. The existing catalog defines controlled choices. Staff controls email, role, privileges, Adviser/group assignment, workflow stage/status, PI/IERB/protocol/requirements and retention. Research title is optional because the current workflow permits activation without a finalized title. Research groups stay Unassigned until authorized staff uses the established group mechanism.

People screens and administrative Student/Adviser exports show Pending explicitly and preserve absent IDs/names as absent data; row labels use Profile incomplete and a dash. Operational research counts, reports/AI selection, Adviser workloads and workflow notification/deadline audiences exclude incomplete profiles. Admin Pending/Complete filters and existing bulk controls use the same authoritative scope. Adviser visibility remains limited to assigned Students.

Archive invalidates invitation/reset credentials and keeps the completion timestamp unchanged. Pending Restore means active plus Pending, and re-archive restarts normal clocks. Adviser Archive unassigns Pending Students as well as completed Students; later Student completion never restores the old assignment. Hold and all seven-day/six-month/override rules apply to Pending profiles. Pending purge requires the exact invited email when no institutional ID exists, the current Admin password and acknowledgement; single grace override also requires a reason. Bulk purge requires its server phrase and never allows a grace override. Mixed populations retain per-account outcomes and recovery safeguards.

Purge removes Pending profile/login/invitation/reset credentials and owned data. Never-completed purge accountability retains only the immutable role/profile reference, such as student account #123, rather than invited email/name. Bulk UI results use the genuine email for review. Complete Adviser historical attribution remains governed by the existing policy. Restore links are shown only to the authorized Admin; deliver them securely and promptly.

Deploy the reviewed final migration, manifest and application together only after separate approval. Both global and Hostinger scoped verifier modes, database/server/manifest binding, persistent authenticated version-3 evidence, live inventory, foreign-key enforcement and fail-closed behavior are unchanged. Old intermediate-v9 evidence fails the new manifest hash. Generate and install final production evidence only after the exact final v9 migration has been independently reviewed and authorized. This document does not perform those operations.

## Admin lifecycle operation

Active Students/Advisers must be archived before purge. Adviser archive transactionally deactivates the login and makes every assigned Student Unassigned, including archived Students. The confirmation shows the assignment count and refuses a changed count. Student accounts remain intact.

The database in Asia/Manila calculates `archived_at + INTERVAL 7 DAY` for manual eligibility and `DATE_ADD(archived_at, INTERVAL 6 MONTH)` for cleanup, using calendar-month arithmetic with month-end clamping. The three-day approaching warning is evaluated when Admin screens load. Six months makes the account eligible for an explicit Admin cleanup operation. No cron, unattended deletion or guaranteed scheduled warning was added.

During grace, normal purge is disabled. ?Delete Now ? Override Grace Period? is available for one archived account with current Admin password, exact identifier, irreversible acknowledgement and a reason of 5?500 characters. Use a concise operational reason without profile/document contents. It bypasses only the seven-day wait. It cannot bypass Hold, unresolved work, ownership/schema verification, transaction/audit or file safety. There is no bulk override. Normal, override and cleanup audits distinguish `manual`, `grace_period_override` and `retention_cleanup`.

Any Admin can place/remove a structured Retention Hold on an archived account; both changes are audited. Hold blocks every purge method. Restore clears archive/Hold/postponement and records restoration, reactivates the uniquely owned login, rotates credentials to invalidate old sessions, and preserves profile completion. It generates a fresh one-hour invitation setup link for never-accepted Pending invitations; accepted Pending and Complete profiles receive the existing 24-hour password recovery link. Copy that link from the result and deliver it securely to the account holder; restoration does not automatically send an email. If the result was lost, request a fresh password reset. Adviser assignments stay Unassigned until explicitly assigned. Re-archiving starts fresh periods.

Purge is temporarily postponed for actual current/unsubmitted document work (`is_current=1` and `rpms_submitted_at IS NULL`), a notification in Sending state or with a held delivery mutex, or a future Active official deadline owned by the target login. This represents pending review, revision or formal submission, live notification delivery, and live deadline responsibility. Complete the workflow or cancel/review the deadline through its normal Admin tools before retrying. Superseded/formally submitted documents, IERB progress/history and past activity alone do not block purge. Concurrent writers revalidate locked live account state. Postponement records the last diagnostic; live state determines whether the blocker still applies.

Student purge deletes the profile, proven login, reset/setup tokens, all proven owned document versions and AI summaries, IERB history, Student recipient notifications/deadline snapshots, explicit exclusive AI/report outputs, attributable personal audits, and exclusive files. Retained deletion accountability contains the former ID, Admin actor, time, method and override reason when supplied; it does not copy the Student email/title/profile/document into a deletion audit. A recycled old identifier/email does not authorize deleting someone else's unstructured evidence.

Adviser purge removes the profile/login/tokens and detaches remaining assignments and institutional author links. Reviewed-by, uploaded-by, IERB actor, report author and notification sender text stays historical. Own historical notification recipients become `historical_adviser`, with live ID removed and queued delivery cancelled. These records cannot attach to a new same-named or same-email Adviser. Past/cancelled deadlines retain a historical creator name while clearing the login ID. Historical Adviser full-name attribution is allowed.

Exclusive report ownership must be explicit; newly persisted Student Reports record it after locked snapshot validation. Historical aggregate PDFs and aggregate AI outputs remain unchanged, including previously purged members. Legacy Student Reports/AI with unprovable provenance are preserved rather than guessed. Shared files, cross-account version/AI edges, inconsistent login claims or colliding ambiguous legacy documents/recipients refuse the affected account. Resolve provenance in a separately reviewed process. Current exports/reports/workload/metrics query surviving live profiles; the aggregate historical exception does not resurrect a profile.

Admin self-archive/self-delete remains separate and self-only, with another active Admin required. Admin retention, bulk deletion and grace override are unavailable.

## Bulk selection, cleanup and outcomes

Filters provide Active/Archived/All and grace/manual/approaching/cleanup/Hold/postponed states while preserving program, academic, department, Adviser, group and search filters. Select individuals, current page or all matching accounts. Sorting/pagination does not change membership; changing filters/search clears selection. The persistent summary shows population/scope.

The server reconstructs filters, binds an immutable ID snapshot to the current Admin session for 15 minutes, rejects duplicate/injected IDs and unrecognized filters, and caps a population at 10,000 accounts. Preview shows eligible/skipped counts, reasons and Adviser unassignment impact. Bulk purge requires current Admin password, the exact server phrase `PURGE N ACCOUNTS` and acknowledgement. All other bulk actions use `APPLY N ACCOUNTS`. Changes in count, membership, target state or assignment impact require fresh preview/confirmation.

?Retention Cleanup? shows both roles' counts and lets the Admin review/run each role through the same selection/preview mechanism; every target must meet the six-calendar-month rule. Hold/unresolved targets remain excluded. Nothing is purged merely by opening the screen.

Each execution request processes at most 25 independently committed accounts and yields between accounts after a ten-second budget. A single large account can still exceed this time; staging caps it at 2,000 owned document/report records and 256 MiB of existing exclusive files. Narrow scope or obtain an operator-reviewed plan for larger accounts. The UI issues the next chunk explicitly, with progress and per-account results. Retrying the same token/cursor returns cached committed outcomes. Durable audit markers recover a commit whose session checkpoint/response was lost. Same-preview progress remains resumable within the refreshed 15-minute session lifetime; a reload may require a fresh preview of remaining live targets. A busy purge lock or safe per-account failure skips that account without failing other commits. Review skipped targets and make a fresh confirmed preview to retry them. A pending/uncertain file outcome is `recovery_required`, not completed or silently failed.

## Filesystem commit and recovery

Preparation validates safe private basenames, exclusive DB references, regular non-linked files and size/hash, then writes an immutable DB/server-bound manifest under `storage/.purge/<random-job>`. Files move by same-volume rename into quarantine while DB locks remain held. The transaction deletes reviewed dependencies/profile/login and persists mandatory audit plus job. Before commit failure, files are restored before releasing locks, then DB work rolls back. After commit, quarantined bytes are deleted and the job becomes complete. Success is returned only after completion. Already absent source files have no bytes to remove.

If finalization fails, the API returns HTTP 202 with `ok=false`, `committed=true`, `complete=false` and a job ID. An uncertain commit leaves the journal intact. Recovery controls show disk journals and unfinished DB jobs. An Admin reviews the exact job, supplies their current password and acknowledgement. Recovery revalidates schema/evidence/bindings and finalizes a committed job; with a positively absent job and intact exact account/references, it restores uncommitted files. Recovery does not overwrite an existing source or delete a reused source filename. Matching sizes/hashes are required. Missing/corrupt/wrong-server journals, conflicting files or unavailable storage require operator review; do not remove/quarantine directories manually to bypass the gate. Pending journals block further lifecycle changes/writes to the affected account until resolved.

Recovery is explicit, never cron. Check the recovery panel after interrupted requests and before closing an enabled window. Completed DB job rows retain only minimal accountability; private manifests are removed after completion. DDL/privilege changes can block recovery until verified again. Keep quarantine private and backed up with DB state. PHP fsync where available improves manifest durability; abrupt power loss, external filesystem edits, backup inconsistency, external direct SQL and newly introduced writers remain operator risks. A single request cannot guarantee a hard wall-clock bound while hashing/renaming one large account.

Concurrency was validated with disposable MariaDB 10.4.32 under READ COMMITTED and REPEATABLE READ, including actual multipart upload, notification/report snapshot writes and Adviser reassignment. Other versions/writers/isolation levels require staging validation. Hostinger production has not been contacted. The global/scoped verifier implementation is preserved; scoped `complete_visibility=false` remains a limited-assurance prerequisite, not a certificate of inaccessible server state.
